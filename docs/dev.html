Developer guide

Extending the Command Center with your own experiments and analyses.

This is about adding to this application. If you want to talk to a device from your own program, without the app, that is the API documentation and it is published separately.

How the pieces fit

LayerResponsibility
Device clientOne connection: control, sample stream, clock mapping. Knows nothing about experiments.
HubHolds the single connection, runs experiments, serves the page and the HTTP API.
PageRenders controls from what the device reports it can do, rather than from assumptions about a particular device.
RegistriesExperiments and analyses are entries in a registry. Adding one is data plus a function, not an edit to the app.

Three rules that are not negotiable

An experiment never sets instrument settings

The settings a device offers describe the instrument and are chosen by the operator. A protocol that quietly changed them would produce a recording whose settings nobody chose. If your protocol needs a particular setting, document that for the operator. Do not impose it.

Recordings are immutable

A capture is written read-only with a checksum. Analyses never modify it, and filters applied during analysis affect only that analysis. The only operation that removes a recording is an explicit delete.

The device answers for itself

The channel count, the resolution, the rates, whether there is lead-off detection, whether there is a model: all of it is asked over the protocol and none of it is assumed. The page renders its controls from device.profile(), so a control that appears is one the device declared. A table of specific hardware in this application is a defect, and a control rendered from anything but the device's answer is the same defect one layer up.

Adding an experiment

An experiment is an async function registered with a decorator. It declares its parameters, and optionally a pre-registered analysis plan.

@experiment("my_protocol",
            "One line describing what it measures.",
            [dict(name="trials", type="number", default=20),
             dict(name="hold_s", type="number", default=2.0),
             dict(name="note",   type="text",   default="")] + TONE_PARAMS,
            prereg=dict(name="my_protocol", window_s=1.0, min_ratio=5.0))
async def my_protocol(dev, rec, sh, emit, p, ctx):
    conds = ["go"] * int(p["trials"])
    return await _cued_trials(
        dev, rec, sh, emit, p, ctx, label=_lbl(ctx, "my"), conds=conds,
        texts={"go": "Do the thing"}, rest_text="Rest",
        hold_s=float(p["hold_s"]), rest_s=3.0,
        intro="My protocol. Do the thing when told, rest when told.",
        extra=dict(experiment="my_protocol"))

Cued trials

Use _cued_trials for anything event-locked. It shuffles the trial order with a fixed seed and writes that order into the recording, because a subject who can predict the next cue is a different subject.

Every cue that starts a state needs a cue that ends it. Pass rest_text. A protocol that says "clench" and then goes silent reads as "keep clenching", and the contrast the analysis depends on disappears. This has actually happened here.

Sham trials

Interleave a sham condition that cues the subject to do nothing. It controls for the cue itself: the sound, the audio path, and any electrical artifact locked to it. If your effect also appears on sham trials, it is not what you think it is.

What gets written

Raw samples first, then the manifest, then the checksums. Checksums are written last, so a run that dies mid-save leaves no checksum and can never be mistaken for a complete recording.

Adding an analysis

An analysis is a function of a recording label plus keyword parameters, returning a dictionary. It is registered by name with its parameter declarations.

def my_analysis(label: str, window_s=1.0, min_ratio=5.0) -> dict:
    cap = load(label)                 # refuses silently-corrupted bytes
    ev  = events(label)               # cue timestamps, if the run had any
    ...
    return dict(label=label, analysis="my_analysis",
                analysis_version=ANALYSIS_VERSION,
                channels=[...], criteria={...}, verdict="PASS")

ANALYSES["my_analysis"] = dict(
    fn=my_analysis, needs_events=True,
    doc="One line describing what it decides.",
    params=[_n("window_s", 1.0), _n("min_ratio", 5.0)])

Pre-register the criteria

Fix your thresholds before you see the data and return them in params, so the result records what it was judged against. Choosing a threshold after looking makes the result exploratory, and it should say so.

Pair over trials

Compare each trial against its own baseline rather than pooling every epoch. Pooling treats correlated samples as independent and inflates significance.

Give it a renderer

Add a branch to the page's result renderer so your analysis produces a readable table rather than raw JSON. Analyses are also mapped to the experiment that produces them, so selecting such a recording picks your analysis automatically.

Results are cached

An analysis is pure and a recording is immutable, so a result computed once is reused. The cache key covers the analysis, the recording and the parameters. Nothing you write needs to be fast to be usable, but it must be deterministic: the same inputs must always give the same answer, or caching will make it look intermittent.

The HTTP API

The page talks to the hub over these. They are stable enough to script against.

EndpointPurpose
GET /api/experimentsRegistered protocols and their parameters
GET /api/analysesRegistered analyses and their parameters
GET /api/capturesRecordings with their metadata and integrity
GET /api/statusConnection state and the instrument's actual configuration
POST /api/runStart a protocol
POST /api/stopStop the running protocol
POST /api/analyzeRun an analysis over selected recordings
POST /api/configChange a setting the device declared
POST /api/liveStart or stop the live stream
POST /api/scanListen for devices. Each reaches the page as it answers, and nothing is connected
POST /api/connectConnect the one device picked from the scan, by its address
POST /api/disconnectRelease the device
POST /api/contact_checkCheck electrode contact once
POST /api/markerTimestamp an event in the running recording
POST /api/tonePlay a cue, to preview it
GET /api/modelThe device's model and its head slots
POST /api/headSelect a head slot
POST /api/predictionsTurn the model's output on or off
POST /api/identifyBlink the device's light for a few seconds, to tell it from others
GET /api/registersThe converter's registers, raw and in words, for debugging
POST /api/embeddingsCollect whole windows of the model's embeddings from the live stream into a file
GET /api/formatsThe formats the library writes
POST /api/exportWrite a capture out, and report what it cost
POST /api/deleteDelete recordings permanently
GET /wsLive status, samples, predictions, cues and progress

They answer the machine they run on and nothing else. The Host and Origin headers are checked on every request, including the WebSocket handshake, because a page anywhere on the internet can otherwise make a browser reach a server on localhost.

Exporting

Every format comes from intomind.export. This application writes no file format of its own, because a second writer is a second set of rules about what a capture means and the two would drift. The route offers export.FORMATS and returns the exporter's summary unchanged, including its measurement of whether that file returned every sample at the value it was recorded at.
